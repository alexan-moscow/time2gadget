# DECISIONS.md

ADR-лог (append-only), формат как в КЛЮЧ24: `Date:` / `Decision:` / `Reason:` / `Impact:`, блоки разделены `---`.

---

Date: 2026-09-26
Decision: Стек — C# / .NET 8 / WPF. Explicitly НЕ Electron/embedded browser.
Reason: Требование пользователя — лёгкое, быстро стартующее приложение; Electron избыточен для компактного all-in-one desktop-гаджета.
Impact: Весь UI — WPF/XAML. Тэй-иконка требует `UseWindowsForms=true` (см. ниже) как единственное отступление от «чистого WPF».

---

Date: 2026-09-26
Decision: MVVM с ручной композицией сервисов (без DI-контейнера).
Reason: Проект мал (одна ViewModel, ~6 сервисов) — полноценный DI-контейнер (Microsoft.Extensions.DependencyInjection и т.п.) добавил бы зависимость и сложность непропорционально размеру проекта.
Impact: `App.xaml.cs` вручную создаёт сервисы и передаёт их в `MainViewModel` через конструктор. Если проект вырастет — контейнер можно добавить позже без переписывания слоёв (сервисы уже за интерфейсами).

---

Date: 2026-09-26
Decision: Таймер считает время через `DateTime`-метки начала/окончания, не через счётчик тиков `DispatcherTimer`.
Reason: Явное требование ТЗ (BRIEF.md §19) — предотвратить накопление ошибки из-за задержек UI-потока.
Impact: `TimerEngine` хранит `_endTimeUtc`/`_pausedRemaining`; `DispatcherTimer` используется ТОЛЬКО для периодического обновления отображения (~100-200ms), не как источник истины.

Date: 2026-09-26
Decision: Настройки — простой JSON-файл (`System.Text.Json`) в `%APPDATA%\TimerGadget\settings.json`, без базы данных.
Reason: Явное требование ТЗ (BRIEF.md §18) — «не нужно использовать базу данных».
Impact: `SettingsService` — единственная точка чтения/записи; при отсутствии/повреждении файла — тихий откат на значения по умолчанию, без падения приложения.

Date: 2026-09-26
Decision: Системный трей — через `System.Windows.Forms.NotifyIcon` (`UseWindowsForms=true`), не сторонняя библиотека.
Reason: У WPF нет собственного tray API; `NotifyIcon` — стандартный, широко используемый, лёгкий подход (не добавляет тяжёлого фреймворка, не Electron).
Impact: `.csproj` получает `<UseWindowsForms>true</UseWindowsForms>` дополнительно к `<UseWPF>true</UseWPF>`. Единственное место в проекте, где касается WinForms-типов — `TrayService`.

Date: 2026-09-26
Decision: Звук завершения на MVP — `System.Media.SystemSounds.Asterisk`, без бандла собственного аудио-ассета.
Reason: Гарантированно доступно на любой Windows-машине без риска сломанного/отсутствующего файла; собственный звук — точка расширения, не MVP-обязательство (в ТЗ не указан конкретный звук).
Impact: `ISoundService` абстрагирует источник звука — замена на кастомный `.wav` позже не требует изменений в `TimerEngine`/`MainViewModel`.

Date: 2026-09-26
Decision: Горячие клавиши на MVP — локальные для окна (`Window.InputBindings`), не глобальные (system-wide).
Reason: Явно допущено ТЗ (BRIEF.md §10) как приемлемое для первого этапа, с требованием не блокировать будущее расширение.
Impact: Реализовано напрямую без отдельного сервиса на этом этапе; при добавлении глобальных хоткеев позже — новый `IGlobalHotkeyService` (P/Invoke), команды `MainViewModel` переиспользуются без изменений.

Date: 2026-09-27
Decision: Иконка трея/приложения — собственный многоразмерный (16/32/48/256) PNG-in-ICO файл, написанный вручную (ICONDIR/ICONDIRENTRY + GDI+ PNG-энкодинг), а не `Bitmap.GetHicon()`.
Reason: `GetHicon()` — известный баг GDI+ (искажение цветов и потеря альфа-прозрачности через 1-битную маску). Трей теперь берёт иконку через `Icon.ExtractAssociatedIcon` из собственных Win32-ресурсов exe (`<ApplicationIcon>`), а не генерирует её в рантайме.
Impact: `Assets/app.ico` — готовый бинарник в репозитории; при желании поменять дизайн иконки нужно пересобрать файл тем же ручным writer'ом (см. `RingtoneGenerator`/`WavEncoder` — тот же принцип «не тянуть внешний ассет/либу ради простого бинарного формата»).

Date: 2026-09-27
Decision: Аудио — NAudio 2.2.1 (WASAPI), не `System.Media`/`MediaPlayer`; встроенные звонки — процедурно синтезированные WAV (свой `WavEncoder`/`RingtoneGenerator`), не аудио-ассеты.
Reason: `System.Media`/`MediaPlayer` не позволяют выбрать конкретное устройство вывода и не дают честный volume-контроль — а ТЗ требует «куда звонить» (выбор устройства) и регулятор громкости. Версия 2.2.1 запинена явно: последняя (3.1.0) требует net9.0. Процедурный синтез звонков снимает вопрос лицензий/веса бандла на 4 «традиционных/современных» тона.
Impact: `SoundService` — единственная точка воспроизведения (WASAPI per-device + volume); встроенные звонки кэшируются как `.wav` в `%APPDATA%\TimerGadget\Ringtones\` при первом использовании. Пользовательский файл (.wav/.mp3) идёт через тот же `AudioFileReader`, без дублирования пайплайна.

Date: 2026-09-27
Decision: Настройки — одно окно `SettingsWindow`, биндится НАПРЯМУЮ на существующий `MainViewModel` (без отдельной SettingsViewModel и без синхронизирующего слоя).
Reason: Проект остаётся однослойным по ViewModel (см. ADR от 2026-09-26 про отказ от DI) — вторая ViewModel потребовала бы двустороннюю синхронизацию состояния ради экрана настроек, который и так представляет то же самое состояние приложения.
Impact: Изменения в `SettingsWindow` применяются мгновенно (то же самое свойство `MainViewModel`, что видит `MainWindow`). Поведение при закрытии (`CloseBehavior`), звук завершения (устройство/громкость/звонок/своя длительность и интервал/«играть файл целиком»), автор/GitHub/VirusTotal (пока тестовые ссылки — реальные позже по прямому запросу пользователя) — все поля `AppSettings`, персистятся тем же `SettingsService`.

Date: 2026-09-27
Decision: Визуальные эффекты во время отсчёта (Pulse/Flash/ColorBreathe, по умолчанию отключены) реализованы как простые `Storyboard`/`DoubleAnimation` поверх уже существующих элементов (`EffectOverlay` Ellipse, `RingGroupScale` ScaleTransform), а не встроены во внутренности `ProgressRingControl`/`SectorRingControl`.

Impact: `MainWindow.xaml.cs.ApplyRunningEffect()` — единственное место, которое решает, что показывать, по `MainViewModel.IsRunning`/`RunningEffect`.

Date: 2026-09-27
Decision: Кольцо выбора времени уменьшено на 25% (SectorRing 144/112→108/84, ProgressRing 104/98→78/74, EffectOverlay 300→225), а центрирование времени внутри кольца сделано структурным, а не через раздельные Margin.
Reason: Пользователь отметил на глаз, что время визуально не по центру круга. Причина: `RingGroup` (кольца) и `CenterDisplay` (текст времени) были СОСЕДНИМИ элементами с разными явными Height (300 vs 190) при одинаковом `VerticalAlignment="Top"` + одинаковом Margin — при таких разных высотах их геометрические центры расходились (~55px по Y), хотя оба выглядели «якобы центрированными» по margin. Заодно — отдельный явный запрос уменьшить само кольцо на 25%.
Impact: `CenterDisplay` перенесён ВНУТРЬ `RingGroup` как отдельный ребёнок с `HorizontalAlignment="Center" VerticalAlignment="Center"` (без Margin) — теперь центр текста математически равен центру Grid-ячейки, в которой центрируются и кольца, независимо от будущих правок радиусов. Pulse-эффект (ScaleTransform) остался только на подгруппе `RingVisuals` (кольца), не затрагивает текст.

Date: 2026-09-27
Decision: Клик на ДРУГОЙ (не текущий выбранный) сектор во время Running/Paused теперь сбрасывает таймер и запускает отсчёт с временем нового сектора — раньше это было no-op.
Reason: Прямой запрос пользователя: «если нажимаем на другую кнопку времени то таймер сбрасывается и стартует от времени новой кнопки». Повторный клик на УЖЕ выбранный сектор по-прежнему добавляет время (докладка) — это поведение подтверждено пользователем как рабочее и не менялось.
Impact: `ITimerEngine` получил новый метод `Restart(TimeSpan)` — безусловная замена длительности + немедленный `Running`, в отличие от `SetDuration` (которая намеренно блокирована во время Running — используется только для колеса мыши). `MainViewModel.SelectPreset` — третья ветка (Running/Paused + другой пресет) вызывает `Restart` вместо no-op.

Date: 2026-09-27
Decision: Ready-состояние (запуск приложения И нажатие Reset) показывает 00:00, а не длительность последнего использованного пресета.
Reason: Прямой запрос пользователя. Раньше `MainViewModel` при старте вызывал `_engine.SetDuration(последний пресет)`, из-за чего дисплей сразу показывал, например, «20:00» ещё до какого-либо клика — это визуально путало с уже «выбранным и готовым к старту» временем.
Impact: `TimerEngine.TotalDuration` по умолчанию и после `Reset()` — `TimeSpan.Zero` (не последний пресет). `MainViewModel` больше не скармливает `LastPresetMinutes` в engine при конструировании — только подсвечивает соответствующий сектор (`SelectedPreset`) для визуальной памяти, не влияя на дисплей времени. Отсчёт всегда начинается явным кликом по сектору.

Date: 2026-09-27
Decision: Возвращён плотный верхний отступ кольца (`RingGroup`: `VerticalAlignment="Top" Margin="0,16,0,0"`, было `Center` + `Margin="0,0,0,28"`).
Reason: Регрессия из предыдущей правки того же дня («структурное центрирование») — смена на `VerticalAlignment="Center"` для решения ДРУГОЙ задачи (совпадение центра текста и колец) непреднамеренно вернула большой пустой отступ сверху, который уже был убран более ранней правкой «убрать padding по ушам». Пользователь верно заметил регрессию и попросил вернуть отступы «как наверху и внизу».
Impact: Верхний отступ снова 16px, симметричен нижнему отступу `ControlsRow` (`Margin="0,0,0,16"`). Внутреннее центрирование текста (CenterDisplay как ребёнок RingGroup) не затронуто — обе задачи решаются независимо: RingGroup решает СВОЁ положение внутри окна, CenterDisplay/RingVisuals решают совпадение ЦЕНТРОВ друг с другом.

Date: 2026-09-27
Decision: Ширина и высота окна (Normal) уменьшены до 273×341 (было 336×406) — единый отступ 16px со ВСЕХ сторон, включая бока кольца и зазор между кольцом и кнопками.

Date: 2026-09-27
Decision: Иконки шестерёнки/крестика — векторные `Path` (Geometry, Material Design «settings»/«close», 24×24 viewBox), а не символьный шрифт.
Reason: Символьный шрифт `Segoe MDL2 Assets` формально содержит нужные кодпоинты (E713/E8BB — подтверждено программно через `GlyphTypeface.CharacterToGlyphMap`), но WPF на этой машине рендерил их как `.notdef`-«коробку» (пустой прямоугольник с полоской) — подтверждено 4×-кропом скриншота. Причина не выяснена (не стоило того времени), решение — не зависеть от шрифтов вообще. Заодно это даёт «одну сплошную читаемую заливку» и «классическую шестерёнку как в Google», как и просил пользователь — Material-иконки по определению solid-fill.
Impact: `Theme.xaml` — `Geometry.Gear`/`Geometry.Close`; `Style.CornerIconButton` больше не завязан на FontFamily/FontSize. Кнопки в `MainWindow.xaml` — `Viewbox`+`Path`, `Fill` забинжен на `Foreground` кнопки (через `RelativeSource AncestorType=Button`), чтобы hover-подсветка из стиля продолжала работать.

Date: 2026-09-27
Decision: Текст в секторах (`Style.SectorValue`/`Style.SectorUnit`) уменьшен на 25% (15→12 / 9→7); подпись "МИН" на ВЫБРАННОМ (синем) секторе красится в `Brush.TextPrimary` (ярко-белый) вместо `Brush.TextSecondary`.
Reason: Толщина кольца уменьшилась со 32 до 24px в тот же день, что и уменьшение радиусов, а размер шрифта тогда не тронули — текст стал вылезать за внешний радиус. Отдельно: `Brush.TextSecondary` (приглушённый серо-синий) на синей заливке `Brush.Accent` даёт низкий контраст — нечитаемо, хотя на тёмном фоне обычных секторов тот же цвет читается нормально.
Impact: Первая попытка (тем же днём) красила "МИН" по-разному в зависимости от выбранности сектора (ярко на синем, приглушённо на тёмном) — пользователь сообщил, что и на тёмном фоне приглушённый вариант недостаточно читаем. Упростили: `Style.SectorUnit` — единый яркий `Brush.TextPrimary` + `FontWeight="Bold"` + `FontSize=8` для ОБОИХ состояний, без условной перекраски в `SectorRingControl.xaml.cs` (код упрощён обратно, лишняя ветка убрана).

Date: 2026-09-27
Decision: Обнаружена и устранена причина повторяющейся путаницы «пропали кнопки»/«вернулись уши»: пользователь тестировал `bin\Release\...\TimerGadget.exe`, а пересобирался и проверялся скриншотами всегда только `bin\Debug\...` — Release не обновлялся с самого начала этого пула правок.
Reason: Обе конфигурации собираются в разные папки (`bin\Debug\...` / `bin\Release\...`), `dotnet build` без `-c` собирает Debug по умолчанию — Release нужно собирать явным `-c Release`, что не делалось.
Impact: Договорились пересобирать ОБЕ конфигурации при каждой правке (или явно уточнять, какой exe тестируется). Каждая find проверка "готово" отныне должна включать `dotnet build -c Release`, если пользователь тестирует Release-путь.

Date: 2026-09-27
Decision: Подпись "МИН" в секторах убрана совсем — остаётся только число.
Reason: Несколько итераций (общий Viewbox на весь блок → число слишком мелкое; раздельные Viewbox на число/подпись → при увеличении числа "МИН" почти исчезает) показали, что 24px-толщина кольца физически не вмещает одновременно крупную читаемую цифру и отдельную читаемую подпись. Пользователь решил проще — только цифры.

Date: 2026-09-27
Decision: ComboBox в SettingsWindow — полный retemplate (закрытый бокс + выпадающий попап), а не переопределение системных SystemColors-ключей.
Reason: Пользователь — "все контекстные менюшки белые на белом фоне нечитабельны". Первая попытка (переопределить `SystemColors.WindowBrushKey` и т.д. глобально) не сработала — современная тема ComboBox на .NET 8 не читает классические SystemColors для попапа (подтверждено скриншотом: попап остался светлым несмотря на переопределение). Возврат к полному retemplate (как в самой первой попытке) потребовал аккуратности: `ContentPresenter` для закрытого состояния обязательно должен биндиться на `SelectionBoxItem`/`SelectionBoxItemTemplate`/`ContentTemplateSelector`/`SelectionBoxItemStringFormat` — при пропуске любого из них закрытый ComboBox показывает сырой `record.ToString()` вместо значения из `DisplayMemberPath`.
Impact: И закрытый бокс, и попап теперь полностью в тёмной теме приложения, подтверждено скриншотом открытого списка устройств вывода. Заодно исправлены дефолты: `AlarmVolume` 0.8→0.5, `SelectedRingtone` ClassicBell→SoftChime (докладка пользователя).

Date: 2026-09-27
Decision: "Длительность звонка в секундах" + "интервал повтора в мс" заменены на одну настройку — "сколько раз звонить" (1..10, не бесконечно). `AlarmPlayFullFileOnce` убран как ставший избыточным (RepeatCount=1 — то же самое).
Reason: Пользователь — "интервал повтора я понимаю не реализован, надо его убрать". Разбор подтвердил реальный скрытый баг: старый цикл (`RingLoopAsync`) не дожидался фактического завершения воспроизведения, а просто ждал заданный интервал по таймауту — если интервал оказывался короче реальной длины звука, повторы накладывались друг на друга (или разъезжались с ожиданием при более длинном интервале). Count-based модель (проиграть звук ПОЛНОСТЬЮ ровно N раз) естественным образом ограничена и предсказуема — не зависит от длины конкретного файла (важно для пользовательских .mp3 произвольной длины).

**Окно «Заставка и фон экрана»: своя картинка с режимом на каждый монитор (2026-09-30).** По просьбе пользователя раздел «Фон рабочего стола» в настройках заменён кнопкой «Управление заставкой и фоном экрана…» → окно `DesktopBackgroundWindow` (логика `DesktopBackgroundViewModel`, состояние `MainViewModel.Wallpaper.cs`). Сверху — перенесённая галочка «Закрепить фоны» (раздел «Слайд-шоу Windows»); ниже «Фон рабочего стола» одной строкой: список картинок (пусто — приглушённо «Выберите файл»; первый пункт «Выбрать свой файл…» — выбор одного или нескольких jpg/jpeg/png, копии в папку программы: у портативной — `Wallpapers` рядом с exe, у установленной — `%APPDATA%\Time2Gadget\Wallpapers`, как свои звонки), правее — кнопки «Мон1», «Мон2»… (номера как в Windows и в окне профилей), щелчок меняет режим по кругу: растянуть → по размеру (картинка целиком, поля цветом фона Windows) → заполнить (с обрезкой) → по центру (исходный размер) → растянуть; значки — рамка монитора и одна фигура линиями (↔, две вертикали, линии за краями, малый прямоугольник). В конце строки «✕» — снять картинку и режимы, вернуть фон, который был до неё. «Разрешение картинки» из запроса понято как «по размеру» (без обрезки, с сохранением пропорций), т.к. «по центру» — отдельный режим. Устройство: у Windows режим фона один на все мониторы (`SetPosition` глобальный), поэтому для каждого монитора картинка готовится программой точно под его разрешение (`WallpaperService.Render`, EXIF-поворот учитывается), кладётся в `Wallpapers\Generated` с новым именем и ставится на свой монитор «растянуть» — пиксель в пиксель; держится без Тайм2гаджета. Фон до первой своей картинки запоминается (`WallpaperBefore`: картинки по мониторам и режим, либо слайд-шоу с папкой). При смене мониторов/разрешения (DisplaySettingsChanged, через 3 с) картинка перерисовывается, только если что-то реально поменялось. Сброс настроек снимает картинку, возвращая прежний фон. Заставка (screensaver) пока не реализована — ждёт описания. Проверено: служба на двух мониторах (номера совпали с окном профилей, режимы — снимками готовых картинок и экрана, возврат фона); окно вживую на тестовой копии — выбор картинки из списка, «Мон1» → по размеру, «Мон2» ×2 → заполнить, «✕» → «Выберите файл», режимы сброшены, фон пользователя на месте. Прокрутка окна — как у остальных (полоса у края окна).
**Фон: «не отображать», сплошной цвет монитора, «✕» левым и правым щелчком (2026-09-30).** По просьбе пользователя: (1) пятый режим кнопки монитора — «не отображать» (значок — перечёркнутый экран): картинка на этот монитор не ставится. (2) Когда на мониторе нет картинки (её убрали «✕» или режим «не отображать»), к кнопке монитора вплотную прилипает квадратик сплошного цвета; щелчок — 16 основных цветов (палитра в два ряда), выбор сразу заливает монитор. Цвет не выбран — квадратик «пустой» с чертой, на мониторе прежний фон (сначала квадратик рисовался чёрным при прежнем фоне — вводило в заблуждение). (3) «✕» левым щелчком — убрать картинку: на всех мониторах сплошной чёрный (дальше цвет каждого меняется квадратиком); правым щелчком — всегда вернуть фон, который был до своих настроек (без переключения туда-обратно — решение пользователя после уточнения). Устройство: `WallpaperService.Apply` получает план на каждый монитор (`MonitorWallpaperPlan`: картинка в режиме / сплошной цвет / прежний фон монитора, прежний — отрисовывается в режиме, которым его показывала Windows); цвета — `AppSettings.WallpaperColors`. Проверено на тестовой копии: Мон1 до «не отображать» → «пустой» квадратик, прежний фон; палитра → красный — верхний монитор красный; «✕» — оба монитора чёрные, квадратики чёрные; правый щелчок по «✕» — фон пользователя (XnView) на месте.
**«Заставка и фон экрана»: два режима с тумблерами, слайдшоу, экспорт/импорт (2026-09-30).** По просьбе пользователя окно — два режима: «Статичная заставка / сплошной фон» (бывший «Фон рабочего стола») и в конце «Динамичная заставка / слайдшоу». У каждого — тумблер (новый стиль `Style.ToggleSwitch` в Theme.xaml); включён может быть только один: пока включён один, раздел другого приглушён (прозрачность 0,4) и недоступен вместе с тумблером. Тумблер выключен — на мониторах прежний фон (`WallpaperBefore`), настройки режима хранятся; правки статичного режима при выключенном тумблере сохраняются без применения. Для настроек из версии до тумблера (`StaticWallpaperEnabled` = null) — включён, если своя картинка/цвет уже стоят.
Слайдшоу: «Менять изображения» — раз в час (с указанного времени старта или каждый реальный час, по умолчанию), раз в сутки (в указанное время, по умолчанию 9:00, или в начале суток 00:00 — по умолчанию), свой интервал (старт сейчас или старт в указанное время); время — новый `Controls/TimeOfDayBox` из трёх `TimeSpinner` (стрелки, колесо, цифры), интервал — не меньше 10 с. Расписание (`Services/SlideshowSchedule`) — одна формула: смены в «опора + k × период»; шаг 1 — с момента включения или изменения расписания (`Epoch`), дальше +1 на смене, по кругу до последнего заполненного шага среди мониторов; все мониторы на одном шаге; пустой шаг монитора — его прежний фон. Таймер — до следующей смены, но не дольше минуты (после сна и перевода часов выправляется; после пробуждения — проверка сразу). Проверено 14 расчётами (все варианты, переход через сутки) и вживую: шаги по 15 с — Мон2 тёмно-красный → прежний фон (пустой шаг) → картинка; Мон1 — на шаге 3 тёмно-синий; строка «Сейчас шаг 3 из 3 · следующая смена в …».
Кнопки «Монитор N» (подпись — сколько шагов) открывают окно шагов (`SlideshowEditorWindow`, модальное): слева картинки из папки программы одной колонкой с миниатюрами (файл не держится), «✕» — удалить безвозвратно (шаги и статичная картинка с ней очищаются везде; сначала фон убирается с экрана); справа 30 шагов плитками 5×6 — картинка перетаскивается из списка, пустой шаг по щелчку — палитра 16 цветов, у заполненного шага «✕» — очистить, у картинки — кнопка режима (растянуть/по размеру/заполнить/по центру, по умолчанию «заполнить» — добавлено сверх запроса); сверху «Добавить картинки…» и «Скопировать на другой монитор…» (мониторы с галочками + «Применить» — шаги как сейчас в окне, сразу в настройки), внизу «✕» (отмена) и «Сохранить». Проверено вживую: перетаскивание на шаг 4, палитра → зелёный на шаге 5, «Сохранить» → «шагов: 5», тумблер выкл → фон пользователя. «✕» правее «Монитор N»: левый щелчок — убрать шаги монитора (запоминаются), правый — вернуть убранные (толкование «очистить/восстановить» для шагов).
Картинок в папке программы — не больше 30 (`WallpaperService.LibraryLimit`, и для статичной заставки): лишние не копируются, сообщение; та же картинка второй раз не копируется. Экспорт/импорт — отдельный раздел в самом низу (доступен при любом режиме): один zip (`Services/WallpaperPackage`) — все картинки папки программы (images/…) и wallpaper.json с настройками обоих режимов; мониторы — по номерам (на другом компьютере другие устройства). Импорт: картинки — в папку программы (лимит), настройки заменяют свои; вопрос «Применить сейчас?» — «Да» включает режим, который был включён при экспорте, «Нет» — только скопировать. Проверено на уровне службы: архив → импорт в чистую папку — все настройки и шаги на месте, повторный импорт без дублей. Не проверено вживую: диалоги экспорта/импорта и «Добавить картинки», «✕» у мониторов слайдшоу, копирование шагов на другой монитор, удаление картинки из списка (не трогали картинки пользователя).
**Слайдшоу: шагов в цикле, лимиты 30/500, миниатюры, сопоставление мониторов при импорте (2026-10-01).** По просьбе пользователя: (1) в окне шагов сверху между «Добавить картинки…» и «Скопировать на другой монитор…» (одной высоты, 34) — тумблер «Шагов в цикле» (по умолчанию выкл) и ползунок 2–30: включён — шаги после выбранного числа сразу приглушаются (0,3), выключен — длина цикла по последнему заполненному шагу (1 и 5 → 5, только 13 → 13, 1 и 3 → 3, пустой шаг — прежний фон); длина 1 — предупреждение «нужно минимум 2 шага» (в окне шагов и в строке состояния). Длина цикла — своя у каждого монитора (`SlideshowSettings.CycleLengths`); смены для всех мониторов разом, каждый идёт по кругу своей длины (строка состояния: «монитор 1 — шаг 3 из 5, монитор 2 — шаг 1 из 3»). Внизу «✕» и «Сохранить» одной высоты с зазором 6. (2) Лимиты: за раз (выбор файлов — в окне шагов и в статичной заставке) не больше 30 картинок, всего в папке программы до 500 (`BatchLimit`/`LibraryLimit`); превышение — предупреждение, что добавлено. Импорт архива ограничен только 500 (архив переносит всю папку). (3) Список картинок статичной заставки — с миниатюрами, как в окне шагов. (4) Импорт: сначала читаются только настройки архива (`WallpaperPackage.ReadData`), окно «Куда перенести настройки мониторов» (`ImportMonitorsWindow`): для каждого монитора из архива (номер, разрешение — теперь пишется при экспорте, что в нём есть) — выбор текущего монитора или «не переносить»; по умолчанию — тот же размер, иначе тот же номер. Кнопки «Отмена» / «Только скопировать» / «Применить сейчас» (вместо прежнего вопроса). Проверено: сопоставление (номера в архиве переставлены — предложены мониторы по размеру, отсутствующий — «не переносить»); окно шагов вживую — тумблер + ползунок → 8 шагов активны, 9–30 приглушены; миниатюры в списке статичной заставки. Окно сопоставления вживую не открывалось (открывается после выбора архива в системном диалоге).
**Шагов в цикле — число в рамке левее ползунка (2026-10-01).** По просьбе пользователя: «Шагов в цикле» → число в рамке (акцентная обводка) → ползунок. Выключено — число по последнему заполненному шагу («—», если шагов нет), включено — выбранное; пояснение — в подсказке. Проверено снимками: 3 (по заполненным) → тумблер + ползунок → 8.
**Слайдшоу: цикл по большему числу шагов, скорость смены, подсказки (2026-10-01).** По просьбе пользователя: (1) разное число шагов у мониторов — цикл идёт по монитору с большим числом шагов, на мониторе, где шаги закончились, до конца цикла остаётся его последний шаг (прежнее правило «каждый по своему кругу» заменено); предупреждение — в строке состояния и в окне шагов. Проверено вживую: Мон1 — 3 шага (красный/зелёный/синий), Мон2 — 5; Мон1: красный → зелёный → синий, синий держится шаги 4–5 (6 с при интервале 2 с), затем снова красный. (2) «Смена раз в секунду не работает — 3–4 с»: каждая смена рисовала 4K-картинки заново и сохраняла в PNG (~2–3 с); теперь готовые картинки кэшируются по ключу (файл и его дата, размер монитора, режим, цвет) в JPEG 95 (сплошной цвет — PNG), до 120 готовых в запасе — замер: первая отрисовка двух мониторов ~0,5 с, дальше из кэша 2–150 мс. Но и при этом раз в секунду Windows не успевает — у неё своя плавная смена фона, и при частой смене она пропускает картинки (замер: 1 с — видны 2 цвета из 3, ~1,3 с на смену; 2 с — все три по кругу ровно через 2 с), поэтому минимальный интервал — 2 с (`SlideshowSchedule.MinInterval`, подсказка у поля). (3) Подсказка кнопки режима шага: «Сейчас: заполнить. Клик — по центру» (и у кнопок «Мон N»: «Клик — …»). (4) «Менять изображения» → «Смена изображений».
**Слайдшоу: показ своим окном-подложкой с эффектами смены (2026-10-01).** Через фон Windows эффекты не сделать (Windows меняет фон сама, одним способом, и раз в секунду не успевает). По решению пользователя — два способа показа: основной «своим окном-подложкой» (`Services/WallpaperUnderlay`) и запасной «средствами Windows (без эффектов)» — на случай ограничений/изменений Windows. Подложка — как у Wallpaper Engine/Lively: окно Проводника WorkerW между фоном и значками (сообщение 0x052C окну Progman; в Windows 11 24H2+ WorkerW — дочернее окно Progman, до этого — следующее окно после окна с SHELLDLL_DefView), в нём на каждый монитор — дочернее `HwndSource` с двумя картинками (нынешняя и новая), место и размер — в физических пикселях. Эффекты (строка «Эффект смены» сразу под «Смена изображений»): мгновенно, плавное растворение (по умолчанию — ближе всего к смене Windows), сдвиг, шторка, наплыв; ≈0,7 с, CubicEase. Экономно: картинки берутся готовыми из кэша (`WallpaperService.PrepareFiles`), рисование только во время смены. Замер: без слайдшоу — 142 МБ, ЦП в простое на уровне шума; подложка со сменой раз в минуту — 217 МБ (две 4K-картинки в памяти), ЦП за 20 с простоя 188 мс (<1% ядра, вместе с часами программы). Минимальный интервал: подложкой — 1 с, средствами Windows — 2 с. Проводник перезапустился — при ближайшей проверке (≤1 мин) подложка встраивается заново; встроиться не удалось — показ средствами Windows и пометка в строке состояния. Выход из программы — на место подложки текущий шаг обычным фоном Windows (`OnAppExit`); выключение слайдшоу/сброс — подложка убирается, фон — прежний. Проверено вживую: 1 с, растворение — промежуточные цвета при смене (красный → FA0300 → 8B3A00 → 057D00 → зелёный), 5 шагов за 4,75 с, значки рабочего стола поверх подложки, после теста — фон пользователя. Остальные эффекты вживую не смотрели (только растворение).
**Способ показа: по умолчанию — средствами Windows; порядок меню (2026-10-01).** По решению пользователя способ по умолчанию — «средствами Windows» (`SlideshowSettings.UseUnderlay` = false). В строке «Эффект смены» сначала способ показа, за ним эффект; ширины меню — по самому длинному пункту. Средствами Windows эффект выбрать нельзя — Windows даёт только свою плавную смену (выключается лишь вместе со всеми анимациями системы), поэтому вместо списка эффектов — неактивное «плавно (как в Windows)». Средствами Windows чаще раза в 2 с не работает визуально (замер: 1 с — видны 2 цвета из 3), поэтому интервал в настройках не меньше 2 с: меньше — поле само поправляется, при переключении на Windows короткий интервал поднимается до 2 с, сохранённый меньший показывается как действующий (2 с). Проверено снимком: «средствами Windows | плавно (как в Windows)», интервал 1 с из настроек показан как 00:00:02.
**Эффекты из частиц: пиксельное растворение, дисперсия, распад (2026-10-01).** По просьбе пользователя — без шейдеров и графических движков (`Services/ParticleTransition`, только при показе своим окном-подложкой): старая картинка режется на кусочки (у каждого — замороженная `ImageBrush` с участком картинки), новая сразу под ними, слой рисует кусочки в `OnRender` по кадрам `CompositionTarget.Rendering` только во время смены и убирается. Пиксельное растворение — сетка 64 столбца, квадраты исчезают в случайном порядке (0,9 с); дисперсия — 40 столбцов, куски сдувает волной слева направо вправо с вращением и затуханием (1,3 с); распад — мелкие частицы (72 столбца, ≈1,5–2,2 тыс.), уносятся вверх-вправо по дуге, уменьшаются и гаснут (1,5 с). Новая смена во время идущей — идущая доводится мгновенно. Проверено вживую плотными кадрами: все три видны (распад — частицы открывают новую картинку слева направо, дисперсия — вращающиеся куски уходят вправо, пиксели — квадраты исчезают). Нагрузка при смене каждые 3 с на двух 4K-мониторах в среднем: пиксели ~21%, дисперсия ~19%, распад ~39% одного ядра (72 столбца вместо 96 почти не изменили — основное время уходит на загрузку двух 4K-картинок и подготовку слоя при каждой смене); между сменами подложка ничего не делает, при интервалах в минуты и часы нагрузка незаметна.
**Эффекты из частиц — ускорение и защита от падения (2026-10-01).** Замер показал, что загрузка картинок почти ничего не стоит («мгновенно» и «растворение» — ~5% ядра при смене каждые 3 с), всё время — отрисовка частиц. Ускорение: (1) у дисперсии и распада волна идёт слева направо — столбцы, до которых она не дошла, рисуются одним куском старой картинки, а не частицами; (2) не больше 30 кадров в секунду; (3) частицы берут участки из уменьшенной копии картинки (не шире 1600 точек). Замер (смена каждые 3 с, два 4K-монитора): распад 39% → 29% ядра, дисперсия 19% → 11,5%, пиксели 21% → 14%; кадры распада на глаз те же, шва на границе волны нет. В первой версии ограничения кадров было переполнение (`TimeSpan.MinValue` в вычитании) — программа падала при первом кадре эффекта; исправлено, а кадр и отрисовка эффекта теперь в try/catch: ошибка в эффекте доводит смену без анимации, программа не падает. Многопоточность: WPF рисует только в потоке окна, частицы одного монитора распараллелить нельзя; можно дать каждому монитору свой поток — смены на двух мониторах пойдут параллельно на двух ядрах (плавнее), но суммарная нагрузка не уменьшится — пока не делали.
**Подложка: каждый монитор — в своём потоке (2026-10-01).** По просьбе пользователя: если ядер больше одного, окно подложки каждого монитора создаётся в своём потоке (STA + свой Dispatcher), загрузка картинки и эффект смены — там же; смены на мониторах идут одновременно, Windows ставит потоки на разные ядра. Одно ядро — всё в основном потоке, как раньше. Ошибка в потоке монитора перехватывается (UnhandledException → Handled), смена доводится без анимации. Выключение: окно закрывается в своём потоке (`Dispatcher.Invoke` с таймаутом 2 с), поток завершается. Суммарная нагрузка не меняется (распад ~31% ядра при смене каждые 3 с), меняется распределение по ядрам. Проверено тестовой программой на 32-ядерном компьютере: показ — 2 окна подложки (каждое в своём потоке), смена с распадом, `Hide` — 0 окон, на экране — фон пользователя без «застывшей» картинки; вживую в программе — распад на двух мониторах (кадры), программа не падает, главное окно отвечает быстрее 100 мс всё время.
**Компактное окно прыгало у края монитора и терялось между мониторами (2026-10-01).** Пользователь: при перетаскивании компактного окна к краю оно моргало, прыгало и пропало (не разворачивалось из трея). Причины: (1) окно двигалось вручную — сдвиг мыши в пикселях экрана прибавлялся к Left/Top в единицах WPF; у мониторов пользователя разный масштаб (100% и 125%), на границе единицы менялись — окно прыгало туда-обратно; (2) проверка «видно ли окно» шла по общему прямоугольнику всех экранов, а у мониторов разного размера в нём есть «дыры» — сохранённое место (3426, −141) было в такой дыре, окно считалось видимым и показывалось за экраном. Исправление: после сдвига мыши на несколько точек перетаскивание отдаётся Windows (`DragMove`) — оно правильно проводит окно через мониторы с разным масштабом (щелчок по центру без движения по-прежнему переключает вид); `EnsureOnScreen` — окно хотя бы 40×40 пикселей в рабочей области монитора (`MonitorFromRect`/`GetMonitorInfo`, физические пиксели), иначе — на ближайший монитор и место запоминается; вызывается после запуска, показа из трея, перетаскивания, смены вида и смены мониторов. Проверено вживую (тестовая копия, настройки — копия и возврат): место (3426, −141) → при запуске окно на экране (3426, 0); перетаскивание мышью с основного монитора на верхний (125%) — окно идёт за мышью с постоянным отступом, на границе один раз меняет размер 181×115 → 226×144, без прыжков. Окно пользователя (1.0.8) возвращено на экран вручную (SetWindowPos) — в установленной версии ошибка останется до следующего выпуска.
